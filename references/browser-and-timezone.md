# AdsPower、BrowserScan 与时区

## 看用户实际浏览器

先找实际 AdsPower profile 和正在运行的 SunBrowser/其他内核。不要用模型服务端网页抓取、普通 Chrome 或新建独立浏览器的结果代替用户环境。Web 工具拿到的 BrowserScan 默认分数/占位值不是用户检测值。

通过可用浏览器/UI 工具读取当前页面、扣分说明、出口 IP、IP 归属时区、浏览器 JavaScript 时区、日期/偏移、WebGL 报告。页面 AX 未显示数值时查看截图；保持 UI 观察可追溯，不读取账号凭据、Cookie、浏览历史或完整启动参数。

只请求“怎么看/怎么改”时先给准确路径；没有修改授权不保存或重启 profile。用户授权实施后，只改指定环境，保留原值、未保存页面和恢复方法，不自动调整整台 Mac 的时区。

## 四层值分开记录

| 层 | 取证位置 | 含义 |
|---|---|---|
| 系统 | 当前本地时间、UTC、实际时区 | 设备墙上时钟与时区 |
| 配置 | AdsPower 环境 → 指纹配置 → 时区 | 基于 IP / 真实 / 自定义的意图 |
| 启动资料 | 该环境启动页、代理检查 | 启动时识别的 IP/位置与生成资料 |
| 实际网页 | 同一环境刷新后的 BrowserScan/时区检测 | 网站实际读取到的 JS 时间和时区 |

设置显示“基于 IP”并不保证浏览器已生效。若启动页显示纽约而网页仍显示 Singapore，结论是配置/启动资料与运行结果不一致；不能无证据归因用户没勾选、代理失效或系统时间漂移。

## 已基于 IP 但不一致的排查顺序

1. 确认页面属于目标 profile，不是普通浏览器或另一个同名标签。
2. 读当前环境时区和代理类型，点该环境的检查网络，记录出口及地区。`No Proxy` 只表示环境未单独配置代理；系统/TUN 仍可能令实际出口在海外，必须实测。
3. 对照启动页和网页时间，刷新检测页排除旧结果。区分 `Intl` 时区标识、`Date` 的 UTC 偏移及同一时间戳；只看到时区名字不同不能断言时钟跑偏。
4. 用户授权且保存工作后，关闭并重开**整个环境**再测；仅刷新网页不等于重新应用启动指纹。
5. 仍异常时，按用户意图试自定义 IANA 时区（例如美国东部出口可用 `America/New_York`），保存并重开后复测。不要只写固定 GMT−5，以免夏令时变化造成错配。
6. 自定义仍未生效：检查当前内核/补丁的已知问题、冲突扩展、持久设置与运行窗口代次；只在授权范围内做最小变更。必要时报告厂商问题，不能反复改系统时间掩盖问题。

既往只读检查出现过“基于 IP、启动资料纽约、网页新加坡”的现象；其根因和自定义修复未被实测证明。不要把该现象固化为某版本必现 bug 或承诺上述步骤必然修复。

## 系统时间解释

纽约 UTC−5 与新加坡 UTC+8 在标准时季节相差 13 小时；这可以是同一时刻的两种显示，不是时钟慢了 13 小时。美国夏令时期间差值不同，用当前日期与时区规则计算。NTP 校时、系统时区、浏览器指纹时区、AdsPower 软件界面时区分别处理。

查询系统时间优先只读本地时钟/UTC和系统时区配置；`systemsetup` 提示需要管理员时，不能因为进程 exit 0 就声称查询成功。除用户明确要求，不调整系统时间服务或定位权限。

## WebGL 与检测分数

`Google Inc. (Apple)` 和 `ANGLE (... Apple M4 ... Metal ...)` 可以是 Chromium 在 Apple GPU 上的正常信息，本身不证明泄漏、时区异常或虚假硬件。WebGL 报告哈希是浏览器指纹摘要，不是公网 IP。

扣分只按当前网站明确列出的项目解释，例如“时区不同”“WebGL 元数据不一致”；没有看到细则不能推算扣分。检查 GPU 元数据、WebGPU、UA/内核、操作系统和实际硬件是否一致；不要靠随机噪声承诺变成真实住宅设备或保证账号安全。

时区修复不等于所有扣分修复；检测站评分也不等于目标服务的政策判定。以修改前后同环境实际结果记录改善，不承诺封号规避或 100 分。

## 菜单核对

常见入口是“环境管理 → 目标环境 → 更多 → 修改指纹/编辑环境 → 时区”，但给用户操作路径前先看当前版本；个人设置的“软件时区”不是 profile 指纹时区。
