# macOS 安全事务、PF 与模式切换

本参考规定执行时必须满足的约束。受支持设备的可执行安装器见 [automation.md](automation.md)；其他设备仍需原生适配，不能复用历史机器脚本中的地址、UID 或绝对路径。

## 先决定关闭语义

用两个独立的布尔选择记录策略，不仅记录模糊的“自动模式”：`native_on_both_off`（两开关都关闭后恢复原网络）、`native_on_gui_exit`（GUI 消失后恢复原网络）。新用户需明确选择；已授权的选择直接沿用。下表列出完整组合：

| 两开关关闭后恢复 | GUI 退出后恢复 | 两开关均关闭 | GUI 退出/崩溃 |
|---|---|---|---|
| 否 | 否 | 保持防护，需明确解除操作才能恢复原网络 | 保持防护 |
| 是 | 否 | 确认关闭意图和运行态后恢复原网络 | 保持防护 |
| 否 | 是 | 保持防护 | 恢复原网络 |
| 是 | 是 | 确认关闭意图和运行态后恢复原网络 | 恢复原网络 |

所有组合中，GUI 仍在、开启意图仍在而 TUN 意外故障时都保持防护；单独关闭系统代理、TUN 仍健康时继续按规则分流。仅节点断线、健康检查超时、设置暂不可读或 API 无响应，都不能独立触发恢复原网络。

检测“GUI 不存在”不能可靠识别主动退出还是崩溃。只要选择 GUI 退出后恢复，就必须说明意外退出也会放行；第 11 项验收恢复原网络，不能沿用严格阻断结论。

恢复原网络意味着解除本工具的代理接管/防护并恢复基线代理和 DNS，并不是只恢复国内站点。已打开的海外网页可能后台重试，新建连接若能从原网络到达目标就可能使用本地出口；不能承诺该模式仍保持海外域名断网保护。若用户要求退出后仍保留这项保护，应重新确认不同方案，不能在同一个模式中混称两种效果。

## 备份与离线还原

1. 创建 `~/clash-guard-backup/<日期时间>/`，记录实际绝对路径、桌面用户/UID、客户端及核心版本。
2. 完整备份客户端配置目录（含订阅、全局扩展、GUI 设置、数据库/缓存文件的必要状态），保留权限。保存系统代理、DNS、网络服务、路由、自启、服务/PF 当前状态和本次将变更文件的清单/哈希。运行时快照注明一致性限制；首次停客户端后可补一份一致快照，不能覆盖最早原始备份。
3. 生成离线 `restore.sh`，附所需备份和恢复工具。使用系统可用的解释器；不在断网后安装依赖或访问远端。
4. 还原流程逐步捕获错误，单步失败仍继续其余步骤，不在恢复段使用导致提前退出的无保护 `set -e`。脚本可重复执行，并以汇总状态报告未恢复项。
5. 区分本次变更的恢复点和首次改动前的全量恢复点：“撤销本次升级”用前者，“回到最初”用最早完整、可验证的后者。

还原顺序按基线区分：回到原本没有本工具防护的状态时，停止本工具自动干预、解除本工具锚点，再恢复客户端、服务、自启、网络代理和 DNS。回到已有防护的健康快照时，先保留/载入 restricted 规则，重启守护并保持 `hold-restricted`，然后恢复客户端；TUN 恢复合格后才解除 hold，不能因 TUN 恢复失败而留下空锚点。每条恢复路径都等真实监听与普通用户健康检查；端口异常时仅处理已确认的本客户端进程，不能杀无关程序。若原状态本来不运行代理，则验证恢复后的原生网络，不强行启动新代理。

## 桌面急救文件

在桌面写 `断网急救.txt`，并将全文发给用户保存。生成时把下面语义占位符换成发现的实际路径/服务名；未替换则不能交付执行。

1. 先打开实际客户端，等一分钟。
2. 不通时在 Terminal 运行：

```sh
sudo sh "/Library/Application Support/clash-guard/off.sh"
sudo sh "<最早完整备份的绝对路径>/restore.sh"
```

3. 文件不存在时仅停本工具服务并清本工具锚点：

```sh
sudo launchctl bootout system/local.clash-guard
sudo pfctl -a com.apple/clash-guard -F all
```

4. 清除实际受影响网络服务的悬空代理：

```sh
sudo networksetup -setwebproxystate "<实际服务名>" off
sudo networksetup -setsecurewebproxystate "<实际服务名>" off
sudo networksetup -setsocksfirewallproxystate "<实际服务名>" off
sudo networksetup -setautoproxystate "<实际服务名>" off
```

DNS 恢复命令必须来自已保存基线：原本 DHCP 才用 `-setdnsservers "<服务名>" Empty`，原有静态 DNS 则恢复其原值。若有确认属于 TUN 的动态 DNS 残留，由本机生成的恢复脚本按所有者和具体 key 删除，不写泛匹配全删命令。

5. 网络恢复后回原对话说“网断过，先查现状再继续”。

卸载/恢复工具不要全局 `pfctl -d`、`pfctl -F all` 或覆盖 `/etc/pf.conf`。`off.sh` 仅解除本工具防护；它本身不等于恢复全部代理/DNS。

## 网络中断必须是独立事务

同一脚本完成：锁定/防并发 → 保存当次状态 → 设置本地故障恢复器 → 停客户端 → 原子替换准备文件 → 重开 → 发现实际核心/端口 → 等 TUN 与 DNS → 普通用户健康检查 → 提交或回滚。不要在客户端运行时改其会回写的配置。

所有外部命令有超时，每一步记录时间、阶段、exit 和脱敏摘要。健康验证用 120 秒总预算，超时自动恢复；恢复器即使 shell 被意外终止仍能执行。普通节点下线与外部断网不保证能靠回滚修复，失败必须诚实记录。

这种自动回滚仅用于安装、修改和故障演练事务，回到该事务批准的基线。日常节点健康监测不得因海外探针失败调用 `off.sh` 或还原到无防护网络；正常运行中的节点故障应保持选定出口和防护策略。

普通脚本用独立 `nohup`/等价方式；管理员脚本交给用户用 Terminal 一次执行 `sudo sh "<实际脚本>"`，不要自行运行 sudo 或要求用户贴密码。先完成无 sudo 的 `sh -n`、`pfctl -n`、`plutil -lint`、解释器/命令绝对路径检查以及实际配置生成/读回验证。工具权限不够时如实区分语法未验和真实运行未验。

涉及停/启、TUN 切换、服务安装卸载、出口切换、演练与还原，都遵守此事务约束。普通 UI 只读检查不需要制造事务。

## PF 的执行前提与边界

固定约定：目录 `/Library/Application Support/clash-guard/`；解除脚本 `off.sh`；子锚点 `com.apple/clash-guard`；LaunchDaemon Label `local.clash-guard`。在使用这些名字前检查是否已有同名部署，备份并识别所有权。

- 在本机核心已以 root 运行、实际 TUN 存在且第 1～6 项验收完成后，才允许安装。
- 读取**当前已加载**的 PF 主规则、锚点、启用状态及 states；不只看磁盘 pf.conf。确认主规则确实调用 `com.apple/*`，评估此前 quick pass 是否绕过子锚点。
- 不存在父钩子时不要仅装子锚点后声称生效，也不擅自覆盖主规则。报告阻塞；只有另有明确授权的、可验证的主规则修复才做。
- 验证 API socket 与精确 root 核心 PID/可执行文件关联，再接纳其返回的确切 TUN 接口。不能无条件放行所有 `utun*` 或信任用户可写接口缓存。
- 正常模式仅允许已验证 TUN、批准 LAN/保留范围、必要 DHCP/链路发现和 root TCP/UDP；其余普通用户出站拒绝。临时 TUN 许可宜 `no state` 或使用已验证的状态清理机制，防止旧状态在 TUN 丢失后继续放行。
- 若要求禁止普通程序自带明文 DNS，端口 53 拦截要在宽泛 LAN 放行之前；允许内核经 root 按策略发起合法解析。不自行添加组织 DNS 例外。
- 受限模式在一般 loopback 放行之前，阻断普通用户到本核心所有已知本地 HTTP/SOCKS/mixed 入口，包括 IPv4/IPv6 与相应 UDP。否则 GUI/TUN 消失但 root 核心仍在时，可经 localhost 绕过限制。
- root UID 豁免会同时豁免其他 root TCP/UDP 程序；PF 无法对所有协议同样按 UID 归属。不能声称对恶意管理员、所有 root 代理或错误 DIRECT 决策提供防护。
- 启用新规则前的旧 PF states 可能继续通行。只在授权事务中清理本机相关状态；注明会短暂断开现有连接，不用全局 flush 代替分析。
- 守护检查本锚点是否缺失/变化、PF 是否启用；按预期规则补回，并记录监测周期。开机调度、其他管理员清规则、父锚点移除均可能有窗口，不能承诺绝对零泄漏。
- 安装文件和运行缓存由 root 持有、非组/其他可写，拒绝符号链接；root 服务不执行用户目录或可写 Homebrew 路径中的代码。需要 Python 等运行时先确认可靠且长期存在。

## 双开关自动恢复的状态机

状态至少区分 `protected`、`restricted`、`native`、`transition/error`。开启意图来自客户端保存设置与经验证的运行态；API 失败不是“关闭”。

- TUN 健康且用户要求开启：恢复分流/DNS并挂防护。
- TUN 开关保持开启，但 TUN/核心失效：受限，不能放行。
- 系统代理与 TUN 的关闭意图都可信，且运行态已确认停 TUN：按已批准策略清理本工具代理/DNS、撤销本工具锚点，恢复原网络。
- 只关闭其中一个：不自动进入 native；单独关闭系统代理时 TUN 仍可分流。
- GUI 不在：严格模式受限；只有“退出即恢复”已获选定才执行 native 转换。启动过渡期设有界稳定检查，避免看到一瞬间无进程即放行。

清理前后反复校验意图与进程代次；用户重新开启时中止清理，不能删除刚建立的新 TUN DNS。发现新接口/端口时仅接纳可信核心数据。运行端口动态换位必须同步更新 PF、系统代理、探针和清理范围，不能硬编码 7897 或大范围清掉全部本地代理。

清理系统 DNS 按基线/所有权恢复，不把 DHCP 恢复误写为固定公共 DNS。其他网络服务、PAC、抓包器监听不得顺手删除。

GUI 退出后 root 核心可能被官方服务自动拉起。优先受支持的停止/闲置 API；不得仅 kill 后假定它不会重启。若只能修改服务内部 desired-state，必须审查当前版本/schema/所有者，备份并暂停其写入者、加锁/事务日志、恢复服务就绪，再验证；版本变化就停止，不能复用历史版本内部协议。

## 失败后的处理

按 `实际失败步骤 → 正常恢复是否完成 → 当前 GUI/核心/TUN/PF/DNS/代理 → 根因 → 最小修复` 报告。安装脚本退出 0 但日志含失败，或只有设置状态没有普通用户探测，不算通过。修复后生成新批次，保留旧失败证据。
